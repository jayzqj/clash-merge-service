# 0001 linux.do 专用分组：服务端预选 + 客户端测速

状态：已接受（拷问会话中敲定）。预选条件中的“出口地区”一项 Superseded by 0005。

## 背景

用户经常通过节点访问 https://linux.do/ ，四种症状同时存在：

- 经常出现 Cloudflare 人机验证；
- 白屏或首屏慢；
- 进站后图片、头像、翻页慢；
- 偶尔连不上或超时。

本机实测（经 Clash Verge 7897 端口，当时出口 188.253.118.70，日本，`colo=NRT`）：

- `GET https://linux.do/` 返回 403，带 `cf-mitigated: challenge`；
- `https://linux.do/cdn-cgi/trace` 返回 200，但耗时约 3.4 秒；
- 本机 DNS 把 linux.do 解析为 31.13.76.99 / `2a03:2880:...:face:b00c:...`（受污染），所以必须走代理。

两类症状的成因不同：

- Cloudflare 验证取决于**出口 IP 信誉**，与用户在哪无关，服务端已有的纯净度分数就能衡量；
- 白屏、慢、超时取决于**用户网络 → 节点入口**这一段线路，VPS 上测不出来。

现有分流规则中 linux.do 没有专门规则，落入 `FINAL` 走 `🚀 手动选择`。

## 决策

新增一个 linux.do 专用分组，采用两段式：

1. **服务端预选（本服务流水线）**：只放入满足以下条件的节点，即本轮连通、纯净度达标、出口在离 Cloudflare 近的地区（日本、香港、新加坡、韩国等）。具体阈值和地区另行决策。
2. **客户端测速（Clash Verge）**：分组类型为 `url-test`，测速地址指向 linux.do。这样由用户本机在当前网络下挑选最快的节点，用户换网络（家、公司、手机热点）时会自动适应。

## 备选方案

- **只在客户端测速**：全部节点放进 url-test 测 linux.do。实现最简单，但可能选出延迟低、却总被 Cloudflare 验证的 IP。放弃。
- **只在服务端测速**：VPS 每轮测各节点访问 linux.do 的耗时。结果反映的是 VPS 的网络，看不到国内入口线路的好坏，和用户的实际体验无关。放弃。

## 后果

- 正面：IP 信誉和线路速度分别在合适的位置衡量，用户网络变化无需重新生成订阅。
- 负面：分组成员依赖纯净度分数，ini 看不到分数，只能像 `🎯 纯净优选` 一样在转换后由代码生成（参考 `app/groups.py`）。
- 跟进：
  - url-test 的测速地址需要选一个不会被 Cloudflare 拦截、又能反映 linux.do 线路的地址；
  - url-test 会自动切换出口，而换 IP 容易触发重新验证，需要设计防抖或固定策略；
  - 需要确定哪些域名与 linux.do 走同一规则，至少包括 `challenges.cloudflare.com`，以及可能存在的图片 CDN 域名。
